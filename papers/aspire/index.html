论文精读 · Harness for Robotics · 总体设计

ASPIRE /skills

Agentic /Skills Discovery for RoboticsAgentic Skill Programming through Iterative Robot Exploration

把 Claude Code、Codex 这类编码智能体放进一个专为机器人调试搭的环境：它写 Python 机器人程序，引擎把每一次感知、规划、抓取、控制调用的输入输出和前后关键帧记成轨迹，智能体自己挑着看、定位故障、改程序、再执行验证。验证过的修复写成文字技能，进入跨任务共享的技能库。在 LIBERO-Pro 和 Robosuite 上，每个任务最后交出一份固定的程序，评测时不再调用大模型。

做了什么

Coordinator 按课程挑任务，给每个任务派一个 actor（编码智能体）。actor 在 15 个调试种子上反复「写程序 → 执行 → 读逐原语轨迹 → 修复」；修补陷入局部时，用进化搜索每轮提 K 个候选程序。新起的 verifier actor 只凭技能描述把源任务重新做成功，这条修复才进技能库。最后的程序只在 held-out 种子上跑一次。

放在 Harness 里看

它设计的是整个开发回路：接口（一套 Python 机器人 API 横跨 LIBERO-Pro、Robosuite、BEHAVIOR-1K，真机经 MCP 接入）、观测（智能体自选的逐原语轨迹）、记忆（跨任务技能库）、组织（coordinator / actor / verifier、课程）、反馈（调试种子上的成功率）。所以归在（1）总体设计。

结果

Claude Opus 4.6 驱动时，LIBERO-Pro 三个套件、两种扰动平均 72%（CaP-Agent0 18%，π0.5 13%）；Robosuite 7 个任务 81%（68%）；BEHAVIOR-1K 两个任务成功率都是 88%。LIBERO-90 攒的技能库零样本用到 LIBERO-Pro Long：30.5%（3.8%）。换 Claude Opus 5.5，80 个 LIBERO-Pro 任务平均约 99%。

最该留意的

主结果的比较协议不对等：ASPIRE 在同一个扰动任务的调试种子上反复执行、修改程序后才评测，VLA 没见过扰动任务，CaP-Agent0 每个种子临场生成程序。「+执行引擎」这一级消融同时加了多轮调试和技能库，没有单独测轨迹粒度。同一模型、同一任务不同次运行可以从 0% 到 100%，而各表都是单次运行。

问题 · §1 · 原文 Figure 1

编码智能体会写机器人程序，但看不到程序错在哪，也不记得上次怎么修

Code-as-policy 把机器人行为写成程序，组合感知、规划、控制 API，所以原则上能像软件一样检查、修改、调试。软件工程智能体（Claude Code、Codex、OpenHands、SWE-agent）已经能读执行轨迹、定位错误、改代码。论文认为机器人编码智能体卡在两处：

  • 反馈太粗。一次 rollout 失败只说明任务没成，不说明是感知错了、抓取不稳、规划失败，还是后续恢复失败。已有方法用人设计的固定接口给证据，比如场景级摘要或预定义的观测：给少了，看不到出错的那个原语；给多了，原始画面会把智能体带偏。
  • 经验不积累。任务做完，找到的修复和恢复策略就丢了。论文的说法是：解第一百个任务的智能体，并不比解第一个时更有经验。

作者对照的是人类机器人工程师的做法：回放执行，看感知输出和运动轨迹，定位出错的子系统，改实现，把能复用的恢复办法记下来。ASPIRE 的三个组件分别对应这三件事：执行引擎给证据，进化搜索扩大修复的探索面，技能库保存经验。

方法 · 机器人执行引擎 · §2.1 · 原文 Figure 2

每一次原语调用都留下证据，由智能体决定看哪一段

引擎为每次感知、规划、控制调用记录：调用的 API、输入、输出、返回状态，以及相关的多模态证据（RGB 关键帧、overlay、抓取候选、物体位姿、运动规划结果）。智能体拿不到完整视频：引擎只保留每次原语调用前后的帧，连同对应的 overlay 和返回值。智能体挑和失败有关的调用去看，改程序后让引擎再执行一遍验证。论文把这个「执行 → 诊断 → 修复」的回路叫 iterative debugging。

程序面对的是同一套 API。代码库里 src/cap_harness/providers/ 下是 SAM3（分割）、GraspNet（抓取）、cuRobo（运动规划）、PyRoKi（逆运动学），LIBERO、Robosuite、BEHAVIOR-1K 和真机 YAM 各有一个适配器。

解读这些轨迹是给「写程序的人」看的

MotorMind、HiMe 这类系统里，观测是给在线决策的模型看的，每一步都要读。ASPIRE 的逐原语轨迹只在开发期给编码智能体看；在 LIBERO-Pro 和 Robosuite 上，最终程序在评测时并不读轨迹，它的条件分支和重试逻辑已经写进了代码里。智能体要看什么由它自己决定，这一点和 PyRUA-Lean 只返回程序请求的图像是同一个思路。

方法 · 技能库 · §2.2 · 原文 Figure 3、13 · 附录 F

存的是「什么情况下、怎么修」，不是整段任务程序

每条技能是一段放进上下文的提示：失败特征（failure signature）、何时适用（when-to-apply）、修复策略，必要时附一段代码草图。分类不预设，从验证过的修复里自然长出来：定位、导航、运动原语、物体级抓取、场景理解、调试流程。收音机任务入库的是一条导航恢复模式：「目标位姿落在障碍物碰撞缓冲区里、规划器反复报错时，先换接近方向再重新感知和抓取」，不是「拿收音机」的完整程序。

入库有两道检查：

  1. Actor 报告。结构化的 findings 文件：观察到的失败模式、验证过的修复、可迁移的模式、任务特有的怪癖、调试种子上的成功率。lint_skills.py 先检查提案，省得把 verifier 花在不合格的提案上。
  2. Verifier 复现。新起一个 verifier actor，只拿到这条技能提案，在源任务的部分种子上独立重做，记录每个条目是对的、有缺陷的还是没测到。
  3. Coordinator 把关。检查是否遵守允许使用的 API 规则，只提升 verifier 复现了成功、且可复用的条目。条目带出处：源任务、调试种子、held-out 结果。

技能存成 Markdown 文件：.claude/skills/iterative-debugging/skills/ 下的 grasp.md、localize.md、transport.md、manipulation.md、task-exploration.md，由 README.md 索引。Actor 之间不交换对话历史和原始 rollout，经验只经技能库传递，所以每个 actor 的上下文里只有任务说明、当前程序和当前这次失败的轨迹。

方法 · 进化搜索、课程与反向迁移 · §2.3–2.4 · 算法 1 · 表 12

修不动时换思路：每轮提 K 个程序，留最好的

迭代调试容易困在局部，反复给同一个失败的策略打补丁。进化搜索每一轮让 actor 参考技能库、历史中排名前 3 的程序和它们剩下的失败轨迹，提出 K 个候选程序；每个候选都在调试种子上执行，产生新的轨迹；比当前最好的分数高就替换。最好的候选在调试种子上达到阈值 θ，或者用完 T 轮，就停下。之后从调试历史里抽出验证过的模式，最终程序在 held-out 种子上只跑一次。搜索对象是程序本身，不是任何模型参数。

K、T、θ 的取值论文没有列出；附录只说成功率低于 90% 的任务才触发进化搜索，LIBERO-Pro 上「修复后的程序」和「进化搜索的结果」二选一，用 66–80 号种子作验证集来选。

课程与反向迁移

Coordinator 同时当课程智能体：根据当前技能库决定下一个做哪个任务，可以去补库里的缺口，可以给已有技能一个用在新任务上的机会，也可以趁着新发现去做同一套件里的任务。任务按顺序做，早做的任务只能用到很小的库，所以低分可能只是缺技能。全部做完后，coordinator 允许用完整的库重跑一次早期低分的任务，论文叫 backward skill transfer。结果见「消融与方差」。

实验设置 · §3.1–3.3 · 附录 B、E

三个仿真基准，调试和评测用不同的种子

  • 编码智能体：主结果用 Claude Code + Claude Opus 4.6（1M token 上下文）。模型消融比了 12 个：Claude Opus 4.6 / 5 / 5.5、Sonnet 5.5、Haiku 5.5、Fable 5.1；GPT-6 Astra、GPT-6 Sol、GPT-6 Luna、GPT-6.1 Sol；开放权重的 Kimi K3、Qwen 3.8 Max。Claude 和开放权重模型跑在 Claude Code 里，GPT 跑在 Codex CLI 里。所有仿真实验的环境和 API 固定。
  • 基准：LIBERO-Pro 的 Object、Goal、Spatial、Long 四个套件，各有位置扰动和任务扰动两种设定，每种 10 个任务；Robosuite 7 个接触丰富的任务（2 个双臂）；BEHAVIOR-1K 两个家庭移动操作任务（导航并拿起汽水罐 / 收音机）。
  • 基线：CaP-Agent0（来自 CaP-X，与本文至少有 7 位作者重叠：视觉差分、预定义技能库，每个种子单独生成程序，测试时推理并重试）；端到端 VLA：OpenVLA、π0、π0.5。「Human」是人类专家写的程序（Robosuite、BEHAVIOR-1K）。

解读主结果比的是三种不同的设定

种子固定了物体位姿、干扰物和初始状态。ASPIRE 在目标扰动任务本身的 15 个调试种子上执行、诊断、修改程序（Claude Opus 4.6 不开进化搜索时，60 个任务共 12,214 次仿真 rollout，平均每任务约 200 次），再在另外 50 个种子上评测。π0.5 等 VLA 只在原始 LIBERO 上训练过，没见过扰动后的任务。CaP-Agent0 不跨种子调试，而是在每个评测种子上临场生成和重试。论文在评测协议里写清了这些差别，但摘要里的「最多提升 77%」把它们放在一起比。和零样本最接近的对照是 LIBERO-Pro Long 迁移实验。

疑点「执行引擎」这一级同时加了三样东西

表 10 的说明：「w/o Engine & Evo」是零样本的 Claude Opus 4.6 加 15 个示例程序，「w/o Evo」是「用执行引擎和技能库修过的程序」。从前者到后者，同时多了在调试种子上反复执行的机会、逐原语轨迹和技能库。没有「多轮调试但只给任务级成功 / 失败」的条件，所以这 48 个点里有多少来自轨迹的细粒度本身（论文的核心主张），没有被单独测量。

疑点15 个验证种子选错了好几次

表中标红的格子：进化搜索的程序在 held-out 上明显更好，却被 66–80 号种子选掉了。例如 Spatial 任务扰动「夹在盘子和小碗之间」84 对 8、「木柜上」98 对 46，Goal 任务扰动「酒瓶放柜顶」72 对 14，Spatial 位置扰动「桌子中央」82 对 32。按 held-out 选当然是作弊，论文没这么做；这些例子说明 15 个种子作验证集噪声很大。另外，表 11 Spatial 任务扰动的基线有一格 13%，50 个种子做不出奇数百分比；该列逐项相加的平均是 8.5%，表里写 4.0%。

解读套件平均稳，单个任务不稳

表 25 的三次运行，套件平均 63.1 ± 3.4，看起来很稳；但「打开中间抽屉」是 0 / 100 / 0，「打开抽屉放碗」62 / 0 / 0。ASPIRE 每次运行产出一份程序，程序要么找到了对的策略、要么没有，单个任务的成功率因此接近二值。论文其余的逐任务表、反向迁移、案例都是单次运行。读逐任务的涨跌时，要先想到这个方差。

疑点技能库在同一套件内的作用没有对照

Claude Opus 4.6、Goal 位置扰动、不开进化搜索：带着套件内累积的技能库（表 10）是 47.0%，空技能库的模型消融（表 19）是 55.6%，三次空库独立运行（表 25）是 59.2–67.4%。原文 Figure 9 的图注承认这几处「数值不同」。其他模型：Opus 5 带库 97.0 / 空库 90.6，Opus 5.5 97.0 / 99.2，GPT-6 Astra 97.0 / 94.4。技能库有用的证据主要在零样本迁移实验里。

疑点没有「用旧库再跑一次」的对照

重跑意味着又一轮调试，任务又是按低分挑出来的。从上面的方差看，单个任务重跑一次本身就可能从 0 跳到几十个点（回归均值）。没有用初始技能库再跑一次的对照，+7.6 个点里有多少来自「库更完整」，分不出来。另外，Opus 5 在 Long 上的逐任务表（表 16）「w/o evo」一列已经是重跑后的数字（例如 pos/3 52%），和表 2 的「Post-rerun」一致。

疑点每个条件只有一次调试运行

「到第一次成功的 token」本身方差很大：同一次调试，早一步或晚一步碰上对的修法就差好几倍。三个任务、每个条件一次运行，能说明方向，说不了倍数。抽屉任务的预算是多少，正文没写。

真机上的 System 2 harness（附录 D）

  • 工具：发现与监控（get_capability_graph、get_job、read_operator_messages）；观测与感知（observe 返回状态、相机图像和新鲜度元数据，cap_get_robot_state，cap_localize_object 用文字查询和标定 RGB-D 估几何）；运动与抓取（cap_move_to_pose、cap_move_to_joints、cap_move_synchronized、cap_set_gripper）。cap_move_to_pose 内部用 Mink 做逆运动学、cuRobo 做轨迹规划。

读懂它

这篇真正说明了什么

关键 insight

1. 产出物是程序，大模型的钱花在开发期

LIBERO-Pro 和 Robosuite 上，每个任务交出一份 Python 程序，在 50 / 100 个种子上直接执行，大模型调用全在调试阶段（Opus 5.5 每任务约 132 次调用、$10.8）。这和每个回合都调大模型的 MotorMind、PyRUA-Lean 是两种成本结构。代价是程序一旦定下来，评测回合里就不能看着画面临场改。

2. 关键是能在仿真里反复执行自己的程序

消融里最大的一跳（14% → 62%）来自执行引擎这一级。它同时带来多轮执行、逐原语轨迹和技能库，论文没拆开；但「能在调试种子上跑、看、改」显然是主要来源。这一点依赖仿真器，或者可以低成本复位的真机。

3. 技能是失败驱动的文字，入库要别人复现

技能不是人写的原语，而是「失败特征 + 适用条件 + 修法 + 代码草图」，要由新起的 verifier 只凭这条技能把任务重新做成功才入库。零样本迁移从 CaP-Agent0 的 3.8% 到 30.5%，是技能库有用的主要证据。

4. 模型换代的影响比 harness 组件大

同一个 harness，Opus 4.6 → Opus 5.5，Goal 位置扰动 55.6% → 99.2%；进化搜索对 Opus 4.6 最多加 34 个点，对强模型不超过 2 个点。三个基准都已接近 100%，要继续比较 harness 设计，需要更难的任务。

容易误解的地方

  • 「零样本」只指 LIBERO-Pro Long 迁移实验。主结果的 72%、模型消融的 99% 都在目标扰动任务上调试过（15 个调试种子），只是评测用另外 50 个种子。
  • 「提升 77%」是百分点，而且是 Object 套件两种扰动的平均。
  • 「80 个任务 99%」用的是 Claude Opus 5.5 加进化搜索。主结果的 Claude Opus 4.6 在三个套件上是 72%。
  • 执行引擎的消融不是「粗反馈 vs 细反馈」的对照。见消融一节。
  • 真机部分是演示级的证据。技能迁移三个任务各一次调试运行，魔方三个回合。
  • 正文说 π0.5「在任务改写（paraphrase）下基本崩溃」，但附录逐任务表里的任务扰动是换目标（如「关炉子」「打开底层抽屉」「酒瓶放进碗里」），不只是换措辞。

FAQ

评测时还调用大模型吗？

LIBERO-Pro 和 Robosuite 不调用：一个任务一份程序，直接在 held-out 种子上执行。BEHAVIOR-1K 用增量分块执行，每块代码根据当前多模态轨迹现场生成，大模型在环；真机的 System 2 也是在线智能体。BEHAVIOR-1K 评测时的调用量论文没报告。

和 CaP-Agent0 的根本区别是什么？

CaP-Agent0 出自 CaP-X（与本文至少有 7 位作者重叠）：视觉差分、预定义的技能库，每个评测种子单独生成一份程序，测试时推理并重试，不跨种子调试，也不积累技能。ASPIRE 跨 15 个调试种子调出一份程序，把修复写进会增长的技能库，评测时不重试。

技能库会不会越用越乱？

论文承认这一点：技能只在入库时验证一次，库变大以后不再重新验证，可能过时、重复或误导，在零样本迁移里会伤害个别任务；需要重新验证、剪枝和按任务排序的检索。零样本迁移的逐任务热图里能看到这种波动。

为什么主结果用 Claude Opus 4.6，而不是最好的 Opus 5.5？

正文没有解释。实验设置写主结果「在所有仿真基准上」用 Opus 4.6，较新的模型只出现在模型消融里。结果是主图里 ASPIRE 的数字（72%）远低于摘要后半段的 99%，两者用的模型不同。

进化搜索的 K、T、θ 是多少？

正文和算法 1 只有符号。附录说成功率低于 90% 的任务才触发进化搜索，代码库里有 campaign.py 保存运行设置，但论文没有列出具体值。

局限与疑点

作者承认的，和我们读出来的

论文自己提到的

  • 还不是完全自主的真机终身学习：魔方实验里，人给初始的任务说明、打乱魔方、在回合间复位。真机需要可靠的成功判断、安全复位、安全监控和标定维护。
  • 依赖冻结的大模型：GPT-6 Luna、Claude Opus 4.6、Qwen 3.8 Max、GPT-6 Sol 只有 15–59%，开放权重最好的 Kimi K3 是 78%；最好的结果都来自闭源前沿模型。
  • 预定义的机器人 API 限制了能表达的行为；需要 API 之外的感知、控制或交互能力时，只能低效地近似，或者靠人扩充 API。
  • 技能只在入库时验证一次，库变大后不再重新验证，可能过时、重复或误导。
  • 调试和进化搜索很耗算力：每个任务大量大模型调用和仿真 / 真机 rollout。

我们读出来的

  • 疑点主结果的比较协议不对等：ASPIRE 在目标扰动任务上调试过，VLA 没有。
  • 疑点执行引擎的消融混了多轮执行、轨迹粒度和技能库三样，核心主张没有单独验证。
  • 疑点逐任务结果全是单次运行，而单任务的运行间方差可达 0 / 100 / 0；表 25 缺 Run 2。
  • 疑点技能库在套件内的增益没有对照，Opus 4.6 带库（47.0%）反而低于空库（55.6–67.4%）。
  • 疑点反向迁移没有「用旧库重跑」的对照，按低分挑任务再重跑会回归均值。
  • 15 个验证种子多次选掉 held-out 上高出 50–76 个点的程序。
  • 表 12 与表 10、11 对不上；表 11 有 50 个种子做不出的 13%；表 8、表 9 与正文的均值各不相同。
  • Claude Opus 4.6 的费用与成功率来自不同的运行。
  • 魔方的打乱程度未报告，每步成本随步数自然摊薄，只有 3 个回合。
  • Robosuite 的 Human 数字只在图里；人写的程序在双臂抬起和螺母装配上远好于 ASPIRE（Opus 4.6）。

  • 和 MotorMind（4）：都不训练任何模型。MotorMind 让通用 VLM 每个回合在线输出毫米级的中层动作，靠 Monitor、Verifier 在回合内纠错；ASPIRE 的纠错发生在开发期，评测时程序固定。两篇里同一个 π0.5 基线差别很大：任务扰动下 MotorMind 自己测得 23.3%，ASPIRE 表 5 是三个套件平均 1.0%，基线的跑法不一样。
  • 和 HiMe（3）：都把记忆放在策略外面、用语言写。HiMe 的图文记忆在一个回合内随子任务更新，由大模型增改删；ASPIRE 的技能跨任务、跨本体保存，写入前要被另一个智能体独立复现。
  • 和 τ₀-VLA（5）：都在「承诺之前」评价候选。τ₀-VLA 用世界模型想象候选子任务的后果再提交；ASPIRE 直接在仿真器里执行候选程序（调试种子），评测种子只跑最终程序一次。到了真机上，ASPIRE 没有可以随便试的仿真器，只能真的执行，这也是它真机部分只做到技能迁移和在线学习演示的原因之一。

读这篇会遇到的词

展开术语表
code-as-policy (CaP)
把机器人策略写成调用感知、规划、控制 API 的程序。
coordinator / actor / verifier
三类智能体：coordinator 排课程、管技能库；actor 负责一个任务的写程序和调试；verifier 只凭技能提案独立复现，决定能否入库。
robot execution engine
执行引擎：运行程序，并为每次原语调用记录输入、输出、返回状态和前后关键帧、overlay。
iterative debugging
执行 → 诊断 → 修复的回路，在调试种子上反复进行。
skill library / skill
技能库与技能：失败特征、适用条件、修复策略、代码草图组成的上下文提示，按类别存成 Markdown 文件。
evolutionary search
每轮基于前 3 名程序和残余失败轨迹提 K 个候选，在调试种子上执行，择优替换，直到达到阈值 θ 或用完 T 轮。
debug / held-out seeds
调试种子用于学技能、改程序；held-out 种子只用来评测最终程序。种子固定物体位姿、干扰物和初始状态。
backward skill transfer
反向迁移：全部任务做完后，用完整技能库重跑早期低分任务一次。
incremental block execution
BEHAVIOR-1K 的评测方式：程序分块，每块根据当前轨迹现场生成。
LIBERO-Pro 位置 / 任务扰动
位置扰动改变物体初始布局；任务扰动改变任务目标（例如「关炉子」代替「开炉子」）。
CaP-Agent0
CaP-X 中的编码智能体基线：视觉差分、预定义技能库、每个种子单独生成程序并在测试时重试。
System 2 / MCP
真机上的在线智能体回路；MCP（Model Context Protocol）服务器把白名单内的机器人工具暴露给智能体。
Kociemba solver
魔方的符号求解算法，给出转面序列。
