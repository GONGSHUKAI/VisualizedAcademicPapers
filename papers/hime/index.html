论文精读 · Harness for Robotics · Persistent State / Memory

HiMe

Hierarchical Embodied Memory for Long-Horizon Vision-Language-Action Control

不往 VLA 里塞记忆，而是把记忆和推理按频率拆给三个模型：π0.5 每 0.5 秒出一个动作块，只看当前画面和一句子目标；Qwen3-VL-8B 每 10 个执行步看一眼最近 8 帧，只回答「当前子任务做完没有」；它说做完了，GPT-4o 才被叫醒，去增、改、删一个图文记忆库，并重写子任务计划。

  • 复旦大学 · 上海创智学院 · 华东师范大学
  • arXiv 2607.03449v1
  • v1 2026-07-03
  • arXiv · 代码

做了什么

三层：Executor（π0.5，瞬时记忆，只看当前观测）、Sentry（Qwen3-VL-8B，工作记忆，最近 8 帧的滑窗）、Planner（GPT-4o，情景记忆：一个图文键值库，加一张带 done / current / pending 状态的子任务表）。Planner 用 QUERY / CREATE / UPDATE / DELETE 的 XML 操作读写记忆。只有 Executor 要训练，用了 60 条示范。

怎么比

WidowX-250 单臂夹爪，第三人称 + 腕部两路 RGB。三个长程任务（Object Search、Counting、Rearrangement，各 6–7 个子任务、约 1035–1450 个动作步），每任务每方法 20 次。所有对照共用同一个 Executor 和同一个 Planner 骨干，只改 Planner 拿到什么记忆、什么时候被叫醒。

结果

平均任务进度：HiMe 90，去掉 Sentry 68，FIFO 式 Flat Memory（类 MemER）65，无记忆的 Transient Memory（类 Hi Robot）14；人工给子任务的上限 94。每个子任务的 Planner 调用 1.4–2.6 次，Flat Memory 4.8–6.2 次。

最该留意的

「90%」是完成子任务的比例，不是整任务成功率。Sentry 召回只有约 35%，靠一个间隔没写的定时兜底才不会卡住。GPT-4o 单次调用中位 38.59 秒，比一个子任务的平均执行时长（我们按附录算约 17–24 秒）还长，论文没有报告整任务耗时。

问题 · §1

VLA 只看当下，能记事的大模型又太慢

主流 VLA 按马尔可夫假设建模 p(at | ot, l)：动作只取决于当前观测和指令。长程任务里，决定下一步的信息常常已经不在画面里：盒子里装了什么（看过一眼就盖回去了）、碗里已经放了几勺、桌上的玩具原来摆在哪。论文把这类任务称为 non-Markovian。

作者认为现有两条路线各有硬伤：

  • 训练式记忆：给 VLA 加历史 token、辅助损失或记忆库（引言举的是 SAM2Act 等，相关工作把 MemoryVLA 也归在这类策略层记忆里）。受上下文窗口限制，跨几百步优化长程因果依赖也很难。
  • 让大 VLM 当记忆容器：由 LVLM 存取历史轨迹（MemER）。可实时控制就要低延迟，能部署的 VLM 规模就有上限；模型越小，世界知识和零样本能力越弱。

论文把这对矛盾叫作 frequency-competence paradox（正文另一处写作 frequency-capability paradox）：推理强的模型慢到进不了控制回路，快到能进控制回路的模型推理又不够。它的突破口是一句观察：大部分记忆操作本身不需要高级推理，也不需要广泛的泛化。「这个子任务做完没有」只需一个中等 VLM 看几帧就能判断；真正需要大模型的「记什么、改什么、下一步做什么」只在子任务切换时才发生。于是按时间尺度分层，让最贵的模型调用得最少。

论文还认为，光有静态的分层不够。真实的人机交互有两个特点：一是多模态信息丰富，指令里带着纯视觉轨迹抓不到的约束和偏好，比如「那个红杯子是 Alice 的」；二是高度动态，任务目标和环境状态都会变。只会追加的记忆会堆积过时、互相冲突的条目，所以记忆要能 Add、Update、Delete。

频率阶梯：每一层多久动一次

对数时间轴。圆点为 P50，横线延伸到 P99，竖短线是 P90。控制、推理、Sentry 间隔来自 §4.1；Planner 延迟来自附录表 11；子任务平均时长是我们按附录表 4 的总动作步数 ÷ 子任务数 ÷ 10 Hz 算的。

解读悖论是被「错开」了，不是被消除了

HiMe 没有让 GPT-4o 变快，而是让它的调用频率对齐到子任务的时间尺度。但附录表 11 显示，GPT-4o 单次调用中位 38.59 秒，比一个子任务的平均执行时长（17.1–24.2 秒）还长；换成本地 Qwen3-VL-30B 也要 6.83 秒，约占一个子任务的三到四成。所以「慢」被推到了子任务交接点上。交接时机器人是停下等新子目标，还是继续做别的，论文没有说。

方法 · 三层结构 · §3.1–3.4

三个模型，四种记忆

问题设定：时域 T ≫ 1 的部分可观测序列决策。理想情况下第 t 步的最优动作依赖完整历史 ht = (o0, a0, …, ot)，但连续处理 ht 算不动，所以用一个分层策略 π(at | o0:t, l) 来近似。三层从「不带记忆的执行层」到「长程推理层」，逐层用频率换上下文容量。

四个公式把三层串起来。Executor 在给定子目标 τt 时假设局部马尔可夫：

at ~ πe( at | ot, τt )(1)

Sentry 是一个只在 t ≡ 0 (mod nm) 时开口的门控：

ut = 𝐈[ πs(𝒲t, τt) > δ ]　若 t ≡ 0 (mod nm)；否则 ut = 0(2)

ut = 0 时直接跳过高层推理，情景记忆原样保留 𝓔t+1 ← 𝓔t。ut = 1 是一次「交接」，表示当前子目标完成或已失效，Planner 分两步更新：

qt = fenc( l, 𝒲t ),　ℳret = TopK( 𝓔ct, qt )(3)
( 𝓔ct+1, 𝓔pt+1 ) ← πp( l, 𝒲t, ℳret, 𝓔pt )(4)

上下文记忆的更新由三种显式操作完成：Add 插入新观察到的事实或用户偏好，Update 修订过时条目，Delete 删掉陈旧或冲突的信息。同时 Planner 合成新的计划 𝓔pt+1，从中取出下一个活动子目标 τt+1 交给 Executor。

实现（§3.4）：检索后端是向量数据库，用 OpenAI text-embedding-3 编码文本查询，多模态条目和它们的 caption 嵌入一起存，按余弦相似度检索；K 未披露。hs = 8，nm = 5。

解读记忆只以一句话的形式到达动作模型

π0.5 不读任何历史，所有记忆都被压缩进子目标 τt 这一句话（例如「place the toy duck in left box」）。所以 HiMe 解决的是「下一步该做什么」依赖历史的情况（箱子里有什么、数到第几份、东西原来在哪），而不是「这个动作该怎么做」依赖历史的情况，例如按钮按下前后外观几乎一样（MemoryVLA 的 Push Buttons 例子）。后者在 HiMe 里只能靠 Sentry 判断子任务是否完成来间接处理。

疑点公式和实现有两处对不上

① 式 (2) 写的是「分数超过阈值 δ」，但附录的 Sentry 提示词要求模型直接输出 done 或 not_done 的 XML 标签，temperature 设为 0.6。分数从哪来、δ 取多少都没写。② 式 (3)(4) 里 Planner 用的是 𝒲t，即最近 hs 帧；图 2 和 §4.3 却说 Planner 拿到的是整个子任务期间均匀采样的 8 帧，并用这一点解释 HiMe 与 HiMe w/o Sentry 的差距。缓冲区按什么帧率存帧也没写。

    解读理想情况下每个子任务只该叫一次 Planner

    如果 Sentry 每次都准时报 done，6 个子任务加上开头一次初始规划，共 7 次调用，平均每子任务约 1.17 次。表 2 里 HiMe 的实测是 1.8、2.6、1.4 次。多出来的调用可能来自 Sentry 误报、定时兜底，或用户新指令触发的重规划，论文没有拆分。切到「固定间隔」模式可以看到 Flat Memory 一类做法为什么调用多：Planner 不管进度，按时被叫醒，大部分调用的结论只是「保持当前子任务」。

    疑点Sentry 到底多久看一次

    §3.4 写「monitoring interval nm = 5」，§4.1 写「Sentry is queried after every 10 execution steps of πe」。前者没给单位；后者的「执行步」既可以理解为 10 Hz 的动作步（每 1 秒一次），也可以理解为 Executor 的推理次数（每 5 秒一次）。上面的切换把三种读法都画了出来，召回率低时差别很明显：间隔 5 秒、连续漏检 3 次，就是 15 秒的空转。

    方法 · 记忆怎么写 · 附录提示词

    一条记忆长什么样，Planner 怎么改它

    情景记忆的读写完全靠提示词约束 GPT-4o 输出结构化 XML。附录给出了 Sentry 和 Planner 两段完整提示词，要点如下。

    PLANNER 提示词

    • 记录字段：id、tags、data（type, value）、image_path。每条 2–5 个 tag，分三类：物体（toy_duck、left_box）、位置（table、inside_left_box）、用户偏好（user、lily、likes）。
    • 两轮交互：第 1 轮只能发 QUERY，计划表必须为空；第 2 轮根据查询结果发 CREATE / UPDATE / DELETE，并输出最终计划表。
    • 证据规则：记忆只能来自用户明确说过的话或直接的视觉证据；不许编造记忆，信息不够时优先安排一个 inspect 子任务。
    • 状态变了怎么办：CREATE 一条新记录，再 UPDATE 旧记录把它标成「过去」。UPDATE 本身只用于纠正或细化、不改变时间含义；DELETE 要少用，只删重复或错误。
    • 计划表：每行一个子任务，[done] / [current]（只有一个）/ [pending]，可在括号里附一句目的。动作只有两种写法：inspect …，或 pick up <object> <source> and place it to <target>。
    • 查询策略：优先按 tag 查，每次只查一个 tag。

    SENTRY 提示词

    • 角色：EXECUTION OBSERVER，唯一的工作是判断当前子任务是否完成。
    • 输入：计划表（带 done / current / pending）+ 最近若干帧拼图，每张左半是腕部相机，右半是第三人称。
    • 判定规则按原语写死：Inspect 在机械臂位于箱子上方或伸进箱子、腕部画面能看到箱内物品和黑色箱底时算完成；Pick & Place 在物体已在目标处松开，或机械臂在箱子上方且能看到黑色箱底时算完成；Reset 在机械臂回到 home 姿态时算完成。
    • 场地配合：箱子内底衬了黑色背景，专门为了提高检测对比度。
    • 输出：只能是 <status>done</status> 或 not_done。

    按提示词格式写出的一次第 2 轮输出大致如下（内容是我们按原文图 3 编的示意，字段和标签结构取自附录；图 3 里的子任务写法更简短，如 place the toy duck in left box，这里按提示词规定的格式写）：

    <memory_operations>

    <text>(past) middle box was empty</text><reason>user just put a toy into it</reason></operation>

    <text>a plush toy is inside the middle box</text><image_path>5</image_path>
    <reason>new object observed in frame 5</reason></operation>
</memory_operations>
<plan_list>

[done] inspect middle box
[done] inspect right box

</plan_list>

    解读「Update」其实是「打墓碑」，这解释了消融里差距为什么小

    论文正文说的是 Add / Update / Delete，提示词里对应 CREATE / UPDATE / DELETE，外加 QUERY。按提示词的规则，状态变化时不覆盖旧记录，而是新建一条、把旧的标成过去；DELETE 只删重复和错误。所以 HiMe 的记忆实际上接近一份带时间标记的追加日志。消融里的 No Management 只支持 Add 和 Retrieve，把所有观测都追加进去；它和 HiMe 的差别在于没有「过去」标记、也不做取舍，平均只差 4 分（86 vs 90）。和 FIFO 的差距（68 vs 90）才是大头，也就是「别丢早期信息」比「把记忆整理干净」更重要。

    解读inspect 把「获取记忆」变成了一个动作

    提示词明确要求「不许编造记忆，信息不够就先规划一个 inspect 步骤」，inspect 也是 Sentry 判定规则里写明的三个原语之一。这样，记忆的写入不只发生在「碰巧看到」的时候，而是由 Planner 主动安排机器人去看。这和同专题 SOMA 用可动头部相机先扫描再建记忆、ActiveVLA 主动选视角是同一类思路，只是 HiMe 把它放在了子任务这一层。

    疑点检索到底靠向量还是靠 tag

    §3.4 说检索用 text-embedding-3 嵌入 caption、按余弦相似度取 TopK；提示词却要求「优先按 tag 查询，每次查一个 tag」。两者怎么配合、K 取多少、tag 查询是精确匹配还是也走嵌入，都没有交代。

    三个任务

    任务设置考的记忆能力子任务动作步
    Object Search三个看不见内部的箱子 + 桌上的物品。先检查箱子推断内容，再按内容归置物品；执行中用户往箱子里加新玩具；最后结合偏好取出正确物品部分可观测下靠主动检查形成记忆；环境变化时持续更新6~1450

    读懂它

    这篇真正说明了什么

    关键 insight

    1. 大模型的问题常常是「什么时候问」，而不是「问什么」

    Transient Memory 的 Planner 没有记忆，只因为逐帧被问，就会在子任务之间来回跳；加一个只会说 done / not_done 的门控，平均从 14 到 26。HiMe w/o Sentry 到 HiMe 又涨 22 分。这些增益都不来自更强的推理，而来自让推理只在该推理的时候发生。

    2. 中间层的任务被刻意设计得很窄

    Sentry 只判一件事，判定规则按 inspect、pick & place、reset 三个原语写死在提示词里，场地还专门给箱底加了黑色衬底。这是「大部分记忆操作不需要高级推理」这句话的工程落点：把高频的那一层压到足够简单，8B 模型才扛得住。

    3. 别丢比整理干净更重要

    FIFO 68 → 只增不改 86 → 增改删 90。保留早期信息贡献了 18 分，整理贡献 4 分。限容量时整理才显出更大作用（80 vs 64）。

    4. 图和文字各管一类信息

    空间、识别类信息丢了文字也找不回，靠图；偏好、配比、顺序这类信息从像素里临时抽很难，靠文字。HiMe 每条记录同时带 tags、文字和图像路径，三个任务都最好，只是在偏语义的任务上图像的增益很小。

    容易误解的地方

    • 「90% 成功率」是任务进度。附录表 5 定义 Task Progress 为完成子任务的比例。摘要、结论和图 4 图注都写成 success rate。全部 6 个子任务都完成的试验占多少，论文没有报告。
    • Sentry 不是记忆本身。工作记忆是一个原始帧的滑窗，Sentry 是读这个滑窗的 VLM。它不总结、不存语义，只输出二值判断，并把帧写进缓冲区供 Planner 采样。
    • 「API 调用减少约 3 倍」只对 Flat Memory。三个任务分别是 3.0×、1.8×、4.4×；Flat Memory 与 HiMe 在触发方式和记忆结构上同时不同。
    • 「弥合与人类的差距」指的是人给子任务的上限。Human High-level 是人替代 Planner 逐步给出正确子任务，Executor 不变，所以 94 是这个 Executor 的天花板，不是人类亲手操作的表现。
    • 「自我纠正知识」没有单独的定量实验。摘要说 HiMe 能按人类偏好自我纠正内部知识，这体现在任务设计里（用户中途加物体、改偏好），没有专门的评测或案例统计。

    FAQ

    Executor 怎么知道该做什么？

    它只接收计划表里 [current] 那一行作为子目标 τt，例如 inspect left box 或 pick up snack table and place it to right box。提示词把动作限定为 inspect 和 pick-and-place 两种写法，Sentry 的判定规则里还有一个 reset。Executor 用 60 条示范微调，论文没有说明这 60 条在三个任务、各原语之间怎么分配。

    Planner 思考的几十秒里，机器人在干什么？

    论文没有说明。附录只写「Planner 只在需要时调用，所以推理延迟与高频控制回路是解耦的」。可是 Sentry 报 done 之后，Executor 需要新的子目标才能继续，按常理只能停下等，或者继续执行已经完成的旧子目标。同专题的 TIC-VLA 正面处理了这个问题：慢模型异步运行，动作策略从不等待，并把延迟作为输入显式告诉策略。

    用户的新指令是怎么进入系统的？

    引言写「当 Sentry 检测到显著状态变化或用户意图修订时，Planner 主动更新知识库」，但 Sentry 提示词只判断当前子任务是否完成，不处理语言输入。新指令具体通过什么通道、在什么时刻送给 Planner，论文没有交代。

    为什么 Counting 上加了 Sentry 也只有 23？

    Counting 要按菜谱和份数多轮取料，需要记住已经取了多少。没有记忆的 Planner 在一轮取料之后看不到累计数量，只能按当前画面猜。Sentry 让切换更稳，但补不上这类持久状态，这正是论文用来说明「记忆是必需的」的例子。

    换成开源 Planner 掉多少？

    只在 Rearrangement 上测过：Qwen3-VL-30B 版 HiMe 83.3，GPT-4o 版 87。单次调用从 38.59 秒降到 6.83 秒。但同一组附录实验里，几条消融的方向和主实验不一致（见结果部分的疑点）。

    局限与疑点

    作者承认的，和我们读出来的

    论文自己提到的

    • 只在真机任务上评测，没有配套的标准仿真基准，受控比较和基准级可复现性受限。
    • 任务主要依赖 pick-and-place 这类简单原语，更多样、更灵巧的技能还需验证。
    • 虽有记忆规模和开源 Planner 的补充分析，但没有充分刻画超长时域、更大环境、长期部署下的表现。
    • Sentry 召回低，可能做过头或陷入循环，因此需要定时兜底（§5 Q4）。
    • 任务越长性能越低，三轮 Object Search 掉到 66.7%（附录表 10）。

    我们读出来的

    • 疑点Sentry 召回约 35%，兜底间隔和两种触发各自的占比都没报告，「Sentry 门控」的贡献无法与定时兜底分开。
    • 疑点GPT-4o 单次调用中位 38.59 秒，长于一个子任务的平均执行时长；没有任何整任务耗时数据，「延迟更低」只用调用次数代理。
    • 疑点附录换 Qwen3-VL-30B 后 FIFO（70.0）高于 No Management（63.3），Transient 加不加 Sentry 都是 25.0，与正文结论相反，附录却写「趋势一致」。
    • 疑点HiMe w/o Sentry 同时去掉了触发时机和「整段子任务均匀采样 8 帧」的输入，消融把两件事混在一起。
    • 疑点Sentry 间隔有 nm = 5 与「每 10 个执行步」两种写法，单位不明；𝒲t 的公式（最近 8 帧）与图 2（均匀采样 8 帧）不一致；式 (2) 的阈值 δ 与二值文本输出对不上。
    • 指标名不统一：正文称 success rate，附录定义为子任务完成比例；平均栏的误差线是任务间标准差，没有试验级的方差或置信区间。
    • Memory Hit 的判定方式（谁来判断「所需信息在不在记忆里」）没有说明。
    • 检索在 §3.4 是嵌入向量 + TopK，在提示词里是逐个 tag 查询，K 未披露。
    • 对照组是同骨架变体，不是 Hi Robot、MemER 原方法；Executor 只用 60 条示范，三个任务各分多少没写。
    • 单一平台、单臂夹爪、三个自建任务，每格 20 次；代码已开源，但任务场地和物品需要自己搭。

    • 和 MemoryVLA：两篇都借了认知科学的「工作记忆 / 情景记忆」说法，HiMe 在相关工作里把 MemoryVLA 归为「策略层的检索式记忆库」。MemoryVLA 的情景记忆是网络内部的 token，每步检索、每步写回、端到端训练；HiMe 的情景记忆是外部数据库，只在交接点由 GPT-4o 改写。真机实验两篇都用了 WidowX 和前置 RealSense D435。
    • 和 OptimusVLA：OptimusVLA 的全局先验记忆检索的是别的相似任务的轨迹，用来缩短去噪路径；局部一致性记忆只看上一个动作块。它解决的是「动作生成怎么更快更稳」，HiMe 解决的是「下一步做哪个子任务」，两者几乎不重叠，原则上可以叠加：HiMe 的 Executor 换成 OptimusVLA 即可。
    • 和 SOMA：最接近的一对。两者都是物体中心的记忆，都要先主动观察（SOMA 转头扫描，HiMe 规划 inspect 子任务）再建记忆。SOMA 的记忆是几何化的潜变量，擅长「东西在哪」；它在局限里承认记忆只到物体级，分不清抽屉开 / 关这类语义状态变化，扩展到房间尺度还需要跨空间、时间尺度的分层记忆。HiMe 的记忆是语义化的文字和图片，擅长「东西是谁的、状态变了没有」，但没有任何 3D 几何。
    • 和 Context Architecture 一类：TIC-VLA 面对的是同一个「慢推理 vs 快控制」的矛盾，但做法相反：慢模型（InternVL3-1B）持续异步运行，动作策略从不等待，并把推理延迟和自身位移作为输入告诉策略；HiMe 用事件门控减少慢模型的调用，却没有说明慢调用期间怎么办。RA-VLA 也做检索，检索的是专家示范片段，用来适应新任务，HiMe 检索的是本次任务里自己记下的事实。ActiveVLA 主动选视角和放大，决定这一步「看什么」；HiMe 的 inspect 子任务是同一思路在任务层面的版本，决定「先去看什么、再记下来」。
    • 和（3）结构化执行、（4）评估与反馈两类：MotorMind 和 τ₀-VLA 也在高层维护执行记忆，交给执行层的只是一条子任务或一个动作批次，三篇的调度各不相同：HiMe 由 Sentry 判 done 事件触发 Planner；τ₀ 的高层约每 1 s 异步刷新子任务缓存（低层约 30 Hz），置信度低时才做世界模型搜索；MotorMind 主线串行，Memory Manager 在后台把逐动作日志压成便条，不阻塞执行。三篇都卡在「子任务做完没有」上：HiMe 的 Sentry 判 done 召回约 35%；MotorMind 诊断里通用 VLM 的完成判断只有 47.5–82.5%（二分类），扰动设定下 9% 的回合错误宣布完成；τ₀ 则专门用「记忆滞后 / 超前 / 未察觉的失败」三类扰动样本训练记忆纠错。解读τ₀ 承诺的记忆消融没有给出结果，HiMe 在同一层级骨架下比了无记忆和 FIFO 记忆，在「记忆本身贡献多少」上证据更直接。

    术语表

    读这篇会遇到的词

    展开术语表
    non-Markovian
    最优动作依赖已经看不到的过去信息，不能只凭当前观测决定。
    frequency-competence paradox
    论文的说法：推理强的模型太慢，进不了实时控制；够快的模型推理能力不足。
    Executor πe
    执行层，π0.5 微调而来，输入当前观测和子目标，输出动作块。
    Sentry πs
    哨兵层，Qwen3-VL-8B，按固定间隔看最近几帧，判断当前子任务是否完成，决定要不要叫醒 Planner。
    Planner πp
    规划层，GPT-4o，读写情景记忆并重写计划表。
    瞬时记忆 𝒯t
    Transient memory，只有当前观测 ot。
    工作记忆 𝒲t
    Working memory，最近 hs = 8 帧的原始观测滑窗。
    情景记忆 𝓔t
    Episodic memory，持久存储，分上下文记忆 𝓔c（图文键值库）和过程记忆 𝓔p（子任务计划表）。
    ut / δ / nm / hs
    Sentry 的门控输出 / 判定阈值 / 查询间隔（取 5）/ 工作记忆窗口长度（取 8）。
    handover
    ut = 1 的交接事件，表示当前子目标完成或失效，触发 Planner。
    CRUD
    提示词里的 QUERY / CREATE / UPDATE / DELETE 四种记忆操作，正文称 Add / Update / Delete。
    Task Progress
    完成子任务的比例，本文的主指标（正文称 success rate）。
    API Calls
    平均每个子任务的 Planner 调用次数。
    Memory Hit
    Planner 被调用时，所需信息存在于记忆中的比例。
    Flat Memory
    对照组：定时调用的 Planner + 最近 8 帧 + 历史关键帧 FIFO 队列，类似 MemER。
    Transient Memory
    对照组：定时调用、只看当前观测的无记忆 Planner，类似 Hi Robot。
    Human High-level
    由人逐步给出正确子任务，衡量固定 Executor 能力下的上限。
    open-loop 执行
    预测出 10 个动作后不再看新观测，直接执行前 5 个。
